CricLot — a real-time
auction engine

Host IPL-style private cricket auctions with team budgets, live bidding, and separate host / team / display consoles — every screen driven by one server-authoritative source of truth over WebSockets.

Role Solo — design & build
Type Real-time web app
Stack FastAPI · Next.js · WebSockets · SQLAlchemy
View source Architecture wiki

The problem

A live auction is only fun if everyone sees the same thing at the same instant.

In a private cricket auction, a host runs the room while each team bids for players against a fixed purse. The hard part isn't the UI — it's consistency. Multiple people bid on the same lot within milliseconds, a countdown timer is ticking, and three different kinds of screen (host controls, team bidding, big-screen display) all need to agree on the current lot, the highest bid, remaining purses and squad sizes.

Naive approaches break down fast: client-side timers drift, HTTP polling shows stale state, and letting clients compute anything invites double-bids, over-budget purchases, and squads that exceed their cap.

The approach

I made the server the single source of truth. Clients never decide anything that matters — they send intents ("place bid", "start lot") and render whatever state the server broadcasts back. One authoritative process owns the timer, the current lot, every purse and every squad.

  • Server-authoritative engine — a lot state machine drives the auction; the hold timer resets on each valid bid, and the server alone decides when a lot is sold.
  • Concurrency-safe bidding — every bid is validated against purse, minimum increment and squad cap before it's accepted, then persisted, so two near-simultaneous bids can't corrupt state.
  • WebSocket fan-out — a hub pushes each state change to every connected screen at once, so host, team and display consoles stay in lock-step with no refresh hacks.

Architecture

Clients send intents; the engine decides; the hub fans state back to every screen.

Key decisions

The timer lives on the server

Clients only render the countdown they're told about. Because the authoritative timer resets on each accepted bid, last-second sniping works exactly as players expect and no screen can disagree about how much time is left.

Validate before you broadcast

A bid is checked against purse, increment and squad cap before it becomes state. Only accepted bids are persisted and fanned out, so an invalid bid never flickers onto other screens and can't leave the auction in a bad state.

One message shape for every screen

Host, team and display consoles subscribe to the same state stream and just render their slice of it. That kept the protocol small and made adding a new kind of screen a front-end-only change.

Outcome

1 authoritative source of truth for timer, lots & purses
3 screen types kept in sync from one state stream
0 refreshes needed — live updates over WebSockets
